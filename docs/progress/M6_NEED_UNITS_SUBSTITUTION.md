# M6 — Customer needs and directed substitutions

## M6-T01 — Editable store customer-need catalogue

M5's functional iPhone minimum is accepted after PR #105. This first M6 increment provides `Plus → Unités de besoin` with offline creation, name/description editing, review/deactivation and filtering. Examples explain customer usage (salad, aperitif, fruit to take away) without creating business records automatically or equating needs to Product Master categories, quantities or stock. No product association, substitution relationship or learned score is introduced yet.

Shared strict NeedUnit contracts precede SQLite 27 / Mongo 25 migrations. Stable client UUIDs, store-scoped confirmed codes, origin and local/remote revision policy keep future membership/graph references traceable. Confirmed codes remain reserved after deactivation. User action/history/Outbox commits atomically; server CAS/history/change commits transactionally. An unconfirmed rejected duplicate draft is retained alongside a restored confirmed catalogue and can choose another code without losing its UUID/history. Conflicting edits require an explicit local rebase or remote adoption; superseded actions remain auditable.

Capability needUnits=true protects older applications and an explicit optional bootstrap extension marks one-time catalogue adoption. Old ACK/pull preserve pending changes. UI fields explain validation errors, show local/synchronized/refused/conflict state and preserve deactivated entries under an explicit filter. The five main tabs remain unchanged. Product memberships are the next M6-T02 increment; directed edges/ranking/evidence are later M6 work and the full chat remains M7.

Verification: 505 local tests and 48 isolated Atlas transaction scenarios pass. New coverage exercises schema/usage separation, transactional rollback/restart, ordered revisions and stale ACK/pull, explicit conflict adoption, duplicate-draft preservation/correction, confirmed code immutability, store/origin guards, inactive code reservation and old-client exclusion/capable restoration and concurrent same-code creation converging to one confirmed entity. Lint/strict TypeScript, formatting, API build and iOS/Android exports are required before delivery. Tests create/drop isolated databases only and do not seed the production catalogue.

Physical acceptance pending: create one or two needs offline, close/reopen, rename/describe and reconnect to synchronize. Deactivate a need, verify it hides from the active list but remains under the inactive filter, then explicitly reactivate if desired. Duplicate confirmed codes must be refused clearly; a rejected never-confirmed duplicate can choose another code. The same store must restore the same UUIDs on another capable device. A controlled concurrent rename must require explicit comparison/resolution. Product, sales/waste observation and commercial plan data remain unchanged. Membership selection follows acceptance.

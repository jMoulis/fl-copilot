# M6 — Customer needs and directed substitutions

## M6-T01 — Editable store customer-need catalogue

M5's functional iPhone minimum is accepted after PR #105. This first M6 increment provides `Plus → Unités de besoin` with offline creation, name/description editing, review/deactivation and filtering. Examples explain customer usage (salad, aperitif, fruit to take away) without creating business records automatically or equating needs to Product Master categories, quantities or stock. No product association, substitution relationship or learned score is introduced yet.

Shared strict NeedUnit contracts precede SQLite 27 / Mongo 25 migrations. Stable client UUIDs, store-scoped confirmed codes, origin and local/remote revision policy keep future membership/graph references traceable. Confirmed codes remain reserved after deactivation. User action/history/Outbox commits atomically; server CAS/history/change commits transactionally. An unconfirmed rejected duplicate draft is retained alongside a restored confirmed catalogue and can choose another code without losing its UUID/history. Conflicting edits require an explicit local rebase or remote adoption; superseded actions remain auditable.

Capability needUnits=true protects older applications and an explicit optional bootstrap extension marks one-time catalogue adoption. Old ACK/pull preserve pending changes. UI fields explain validation errors, show local/synchronized/refused/conflict state and preserve deactivated entries under an explicit filter. The five main tabs remain unchanged. Product memberships are the next M6-T02 increment; directed edges/ranking/evidence are later M6 work and the full chat remains M7.

## M6-T02 — Many-to-many product memberships and Copilot-ready batch preparation

The owner accepted the need catalogue after PR #106 and reiterates that the final journey is uploading Mercalys/commercial files and discussing them with the Copilot. This increment therefore exposes one runtime-neutral preparation operation for both native corrections and the future agent, instead of coupling classification rules to screens. The product skill contract lives in `docs/copilot/skills/customer-need-memberships.md`; M7 conversational registration/provider execution is not introduced here.

`NeedMembership` stores a stable store/product/need tuple UUID, independent declared strength/confidence, primary flag, MANUAL/AI_PROPOSED/LEARNED source, PROPOSED/VALIDATED/REJECTED state, explicit human confirmation and version/timestamps. No example score is hardcoded for a SKU, no quantity is represented and no substitution edge or KPI is created. Active products with unknown category/nature/sales unit can be classified; these metadata gaps alone do not block usage membership.

`prepareNeedMembershipBatch` validates explicit numeric declarations and scoped parent snapshots, supports overlapping needs and returns prepared records/skips without side effects. Its trusted actor/decision context is separate from model-controlled request data. AI can prepare proposals only and cannot replace human validated/rejected/manual-draft decisions. Human confirmation or rejection is explicit; unchanged pairs are skipped. The future Copilot can prepare classifications in bulk and ask for meaningful confirmations rather than requiring one manual form per product.

SQLite 28 stores memberships and immutable action history. Selected batch, history and Outbox commit atomically; an invalid later tuple rolls back the whole local batch. Stable SHA-256-derived UUIDv8 identity enforces one logical pair while allowing one product in several needs and several products per need. Mongo 26 checks identity/scope/active parents and human decisions before transactional history/change. Missing unsynchronized parents wait retryably. Equivalent concurrent first creation converges to one canonical membership/history; different declarations produce an explicit same-pair conflict. Rejection remains durable and is never reopened by an automatic proposal.

Capability needMemberships=true gates envelopes and optional bootstrap productNeedMemberships; the legacy needMemberships placeholder stays empty. One-time capability adoption restores previously skipped pairs. Old ACK/pull preserve pending corrections; conflict adoption/rebase preserves old actions and retires superseded commands without active error counts. Parent identity/source references stay traceable. Rejection/removal does not physically delete history or alter products, needs, prices, stock, sales/waste observations or plans.

Product and need details show their memberships. A common batch screen prepares several products for one need or several needs for one product, with search, explicit declared percentages and confirmation. Only checked targets are updated; unchecking does not silently delete unrelated pairs. Existing associations can be explicitly rejected/removed, and refused/conflicting synchronization is visible. Main navigation remains the canonical five tabs. This inspection/correction UI is temporary manual access to the same operations that the M7 Copilot will use.

Physical acceptance pending: from an active need, associate a small selected product batch offline with explicitly chosen values and confirmation; close/reopen and verify pending records. Reconnect and observe synchronization. From a product, confirm it can belong to more than one need. Remove one association and verify its rejected history remains, while other pairs are unchanged. A controlled concurrent change must compare both declarations. Retired/missing/foreign parents must never become validated memberships. Directed substitution relationships remain M6-T03.

Verification: 514 local tests and 52 isolated Atlas scenarios pass, including the new batch proposal/authority guards, overlapping memberships, atomic rollback/restart, ordered edits, stale ACK/pull preservation, explicit conflict adoption, equivalent concurrent creation convergence, retired/missing/foreign parents and old-client exclusion/capable restoration. Existing need catalogue, commercial planning/execution and two-device scenarios remain passing. Lint/strict TypeScript, formatting, API compilation and iOS/Android Hermes exports are required before delivery. No production membership is created by these tests.

## M6-T03 — Directed substitution persistence and batch operations

M6-T02 is accepted on iPhone after PR #107. `ProductSubstitution` now identifies the ordered store/source/substitute/need tuple with a stable UUIDv8. A → B and B → A are independently stored, revised and rejected; self edges and duplicate logical tuples are refused. Sharing a customer need does not automatically create a relationship. Unknown product category/nature/sales unit does not block an explicit compatibility declaration.

SQLite 29 and Mongo 27 provide unique directed-edge scope and immutable action/version history. Local selected batches, history and Outbox commit atomically. `PRODUCT_SUBSTITUTION_UPSERT` uses scoped parent checks, stable identity, optimistic revisions, retryable missing parents, equivalent concurrent-creation convergence and explicit conflict resolution. Old ACK/pull preserve pending corrections. Rejected relations remain durable; no AI proposal may overwrite a human decision. Conflict rebase preserves the canonical remote learned metrics instead of publishing a stale local score.

Declared need/usage compatibility is distinct from price/packaging compatibility, learned relationship score, confidence and evidence. Missing price/packaging values remain null. Until M6-T06/T07 provides the evidence/scoring engine, learned values remain null with zero evidence; they are not seeded from specification examples or equated to user confirmation. Remote observed metrics are read-only to user/AI upsert commands. Manual initial scoring and confidence calibration remain the conservative deterministic M6-T07 work; a confirmed relation is not an observed substitution result.

`prepareProductSubstitutionBatch` is runtime-neutral and side-effect-free. Trusted caller snapshots and human decision context are separate from the model-controlled candidate request. The intended product skill is documented in `docs/copilot/skills/directed-substitutions.md`. This is preparation for M7, not a registered conversational tool or an AI provider call. No substitute or production business record is created by this increment automatically.

The regular product-sheet inspection/correction UI is M6-T04, next. This increment supplies the underlying repositories and a domain-specific synchronization conflict screen; no new mandatory catalogue workflow or primary tab is added. Native tests at this stage are regression checks (existing product/membership flows and synchronization), not manual creation of substitution edges through a new screen.

Verification: 524 local tests and 57 isolated Atlas transaction scenarios pass. Lint, strict TypeScript, formatting, API build and iOS/Android Hermes exports pass. New coverage verifies independent directions, scoped unique edges, self-edge refusal, proposal authority, unknown vs zero, atomic rollback/restart, ordered edits and stale ACK preservation, explicit conflict adoption, idempotent/concurrent creation, parent/store guards, client-authored learning refusal and one-time capable-client adoption. Production preflight finds no existing substitution edges; tests create/drop isolated databases only.

## M6-T02 — Many-to-many product memberships and Copilot-ready batch preparation

The owner accepted the need catalogue after PR #106 and reiterates that the final journey is uploading Mercalys/commercial files and discussing them with the Copilot. This increment therefore exposes one runtime-neutral preparation operation for both native corrections and the future agent, instead of coupling classification rules to screens. The product skill contract lives in `docs/copilot/skills/customer-need-memberships.md`; M7 conversational registration/provider execution is not introduced here.

`NeedMembership` stores a stable store/product/need tuple UUID, independent declared strength/confidence, primary flag, MANUAL/AI_PROPOSED/LEARNED source, PROPOSED/VALIDATED/REJECTED state, explicit human confirmation and version/timestamps. No example score is hardcoded for a SKU, no quantity is represented and no substitution edge or KPI is created. Active products with unknown category/nature/sales unit can be classified; these metadata gaps alone do not block usage membership.

`prepareNeedMembershipBatch` validates explicit numeric declarations and scoped parent snapshots, supports overlapping needs and returns prepared records/skips without side effects. Its trusted actor/decision context is separate from model-controlled request data. AI can prepare proposals only and cannot replace human validated/rejected/manual-draft decisions. Human confirmation or rejection is explicit; unchanged pairs are skipped. The future Copilot can prepare classifications in bulk and ask for meaningful confirmations rather than requiring one manual form per product.

SQLite 28 stores memberships and immutable action history. Selected batch, history and Outbox commit atomically; an invalid later tuple rolls back the whole local batch. Stable SHA-256-derived UUIDv8 identity enforces one logical pair while allowing one product in several needs and several products per need. Mongo 26 checks identity/scope/active parents and human decisions before transactional history/change. Missing unsynchronized parents wait retryably. Equivalent concurrent first creation converges to one canonical membership/history; different declarations produce an explicit same-pair conflict. Rejection remains durable and is never reopened by an automatic proposal.

Capability needMemberships=true gates envelopes and optional bootstrap productNeedMemberships; the legacy needMemberships placeholder stays empty. One-time capability adoption restores previously skipped pairs. Old ACK/pull preserve pending corrections; conflict adoption/rebase preserves old actions and retires superseded commands without active error counts. Parent identity/source references stay traceable. Rejection/removal does not physically delete history or alter products, needs, prices, stock, sales/waste observations or plans.

Product and need details show their memberships. A common batch screen prepares several products for one need or several needs for one product, with search, explicit declared percentages and confirmation. Only checked targets are updated; unchecking does not silently delete unrelated pairs. Existing associations can be explicitly rejected/removed, and refused/conflicting synchronization is visible. Main navigation remains the canonical five tabs. This inspection/correction UI is temporary manual access to the same operations that the M7 Copilot will use.

Physical acceptance pending: from an active need, associate a small selected product batch offline with explicitly chosen values and confirmation; close/reopen and verify pending records. Reconnect and observe synchronization. From a product, confirm it can belong to more than one need. Remove one association and verify its rejected history remains, while other pairs are unchanged. A controlled concurrent change must compare both declarations. Retired/missing/foreign parents must never become validated memberships. Directed substitution relationships remain M6-T03.

## M6-T06 — Daily substitution evidence, versioned lineage and offline inspection

M6-T05 is accepted after PR #110. The shared deterministic engine produces one current evidence record per store/event/directed relation. Only actual USER store observations, scoped products/customer needs and proposed/validated/learning relationships are eligible; rejected/inactive references are excluded without reactivation. Original event timestamps are preserved, while observations use whole Europe/Paris calendar days. Open events, incomplete days, missing/partial candidate sales, invalid/zero/negative reference and probable same-type overlapping duplicate incidents remain explicitly non-actionable. Different concurrent incident types remain contextual records, not duplicate stock quantities.

The v1 measure is Mercalys source sales value in EUR, not quantities or normalized margin. Canonical shared money aggregation is reused from analytics-core. For each observed date, the reference is the mean of available corresponding weekdays at J−7/J−14/J−21/J−28 strictly before the event. Days with a source/candidate incident or a known planned commercial operation are excluded; known mismatched public/school-holiday states are not comparable. Missing sales never become zero; published zero stays zero. All per-day actual/reference values, used IDs/source records and context snapshots are retained. No hourly prorating, inferred stock, lost-volume allocation, uplift or causal claim is produced. Quantities remain null because historical unit equivalence is not asserted.

Positive monetary variation ≥10% yields SUPPORTS_SUBSTITUTION as a qualified hypothesis; other variations remain NEUTRAL. In particular, a negative variation does not weaken a relationship when promotions/weather/context are incomplete. The versioned quality heuristic is reference-count factor (three-plus=1, two=.7, one=.4), whole/partial-day factor (1/.35), declared/proposed relation factor (1/.5), recorded confounder factor (1/.5), calendar-coverage factor (.75/.5), and source-sales-presence factor (1/.8). Strength is min(.5, abs(variation)/100 × quality). These are transparent deterministic information weights, not statistical probabilities or learned relationship confidence; their tuning is separate from facts. A single weak/contextual observation cannot create high global confidence.

Confirmed commercial plans are preserved as planned windows; a matching current-plan/checksum INSTALL_TG declaration is labeled DECLARED_TASK_DONE, not an actual full operation execution period. Market tension remains unknown where no exact trustworthy product context exists. Existing MET data is forecast-only and is never treated as observed historical weather. Only fresh, structurally complete and adequately scoped cached government calendars can qualify holiday context. Absent cache/zone/truncated responses remain UNKNOWN/PARTIAL; no new provider call is required to capture a field observation.

Mongo 29 adds evidence, immutable revisions, scoped processing state and a durable per-event work queue. Relevant source changes enqueue/invalidate work in the same canonical change transaction; corrections and late imports are reconsidered. A signed Inngest recovery function checks ten due events every fifteen minutes, with bounded leases and Mongo snapshot transactions. Consistent input checksums skip unchanged recomputations, including later learned score/count updates; sales corrections preserve the older evidence snapshot while revising the current record. Scope/lease guards prevent parallel/foreign computation. Failed processing preserves previous facts, exposes ERROR and retries later. No relationship score, confidence, evidenceCount or business KPI is changed here; M6-T07/T08 owns conservative model updates/audit.

SQLite 31 replicates read-only evidence and processing state through capability substitutionEvidence=true, explicit optional bootstrap extensions and one-time adoption. Older applications skip these envelopes. Stale snapshots never overwrite newer revisions and identity/store guards protect local scope. Product substitution and event details expose daily comparisons, periods/reference days, per-day snapshots, reasons, lineage counts and a qualified interpretation. Pending/error states preserve existing comparisons while marking them for refresh. This is optional inspection for the future Copilot; no chat/provider execution or extra primary tab is introduced.

Physical acceptance: after a closed past-day signal on A and a declared A→B relation, allow the server recovery run and synchronize. The product/event view must show either a traced daily comparison or its precise waiting/insufficiency reason. Missing relevant Mercalys days or comparable references must never display invented zero. A partial-day incident must explicitly refer to whole-day sales; source prices/promotions/weather gaps qualify interpretation. Reimport a corrected source day and verify the same evidence ID revises after recovery/sync, with updated figures. Explicitly rejected relations cannot learn/reopen. Until M6-T07, the relation's learned score/confidence/count remain unchanged. No artificial production data is seeded for this test.

Verification: 553 local tests and 73 isolated Atlas scenarios pass, including idempotent backfill of USER observations synchronized before this increment. The backfill adds analysis work only, preserving the original event. The focused eight-scenario evidence suite passes after this addition. API compilation, formatting and iOS/Android exports pass; the workspace lockfile changes only the analytics-core link reused by substitution-core.

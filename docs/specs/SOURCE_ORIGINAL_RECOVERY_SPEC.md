# Remote original recovery — V1/L8

An uploaded source original must be recoverable on another authorized device without reimporting, republishing or reconstructing its bytes from normalized observations. This extends the existing source upload/private Blob channel and local original reselection; it does not replace business synchronization or receipt/PDF processing.

The new recovery endpoint requires current authenticated store access. Business originals (Mercalys, waste receipts and commercial PDFs) remain private to authorized store users, consistent with the existing PDF original opener and the ingestion permissions. A `STORE_PHOTO` remains restricted to its uploader/private conversational scope. No public sharing or cross-store access is added. Model arguments never select an actor, store, URL or storage key. Confirmed source/upload/blob metadata, canonical object key, checksum, size and MIME must agree; withdrawn, pending, foreign or contradictory sources yield no download capability. A short private read URL is returned only to the native file transport, never to the model, messages, logs or a durable job payload. Authorization/availability are rechecked before returning a link and before committing a recovered file.

The manifest has stable source identity, authenticated owner/store, exact original metadata and a deterministic metadata hash. Its hash excludes the short read URL/expiry. It is not a signature or business-data authority. The actual downloaded bytes must match the recorded checksum, size and type before being made available locally. Original bytes are immutable; EXIF or receipt photo order are not rewritten. Multi-view receipt bundles retain their original bundle and independently verified original views.

Native recovery uses a durable owner-scoped job and verified SQLite file/manifest metadata. Local reads render existing content without network waits. An explicit original-file action can enqueue recovery offline, resume after restart, refresh an expired download authorization and retain completed copies. Account/store changes, cancellation, invalid bytes, source withdrawal, full storage and uncertain commits cannot overwrite or delete an existing or unsynchronized original. A current local original always takes precedence over downloading a replacement. Missing manifests may be rebuilt from the authenticated original source; domain UUIDs and existing receipt/source file references remain stable.

Restoration changes local file availability only. It must preserve products, identities, observations, receipt edits, source parsing/publication state, versions and pending Outbox commands. No upload, extraction, AI, canonical publication or retry of a refused business command follows merely from recovering a file. New metadata never fabricates a business date, publication, analysis result or a missing amount.

Acceptance spans server policy and real Mongo metadata, valid/stale/withdrawn source proofs, read URL constraints, original size/hash/type, PDF/XLSX/photos/ordered receipt bundles, local metadata loss and restart, ownership changes during transfer, rollback and preserved originals, plus a complete first-device upload → second-device recovery proof. Native rendering, permissions, network and memory behavior remain in grouped device acceptance. No paid provider test, deployment or EAS is implied.

Native original actions share one read/cache path. File hashes use bounded incremental reads, and private department photos retain the existing pixel/decode limits. After asynchronous local verification, source availability, account ownership and retained-file identity are checked again before exposing the file. Unrelated business edits or upload-state changes do not invalidate an otherwise unchanged original.

Original consultation uses a dismissible sheet without replacing the underlying list context. Receipt views are individually navigable and shareable; PDF/XLSX use the native sharing/opening facility only after module availability checks. The signed Blob capability never becomes a public sharing URL. When business metadata arrives later, normal pull handlers may attach a validated matching cache file without publishing or creating business records from file metadata.

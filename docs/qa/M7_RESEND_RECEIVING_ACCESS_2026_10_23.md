# Resend receiving compatibility and credential separation — 23 October 2026

## Actual incident and scope

A real Mercalys email reached the signed webhook and its authorized receipt. Private provider logs show the deployed server SDK's received-attachment GET returns HTTP **401 / restricted_api_key**, with a sending-only-key explanation. The separate connector can read that metadata. No Vercel Secret was decrypted/exported to diagnose the refusal. This establishes an access failure, not an Inngest-quota diagnosis. The sixth attempt is exhausted: the job is DONE but the receipt file is FAILED / PROVIDER_UNAVAILABLE with no sourceDocumentId or proof; DONE here does not mean successful preservation. No original-byte proof, business import or AI result is claimed for that received file.

Successful authenticated metadata also reveals a second compatibility issue: `cdn.resend.app/receiving/{emailId}/attachments/{attachmentId}`, whereas the previous reader only allowed the documented legacy `inbound-cdn.resend.com/{emailId}/attachments/{attachmentId}` example. Supporting the current URL cannot by itself fix the earlier HTTP 401. Both exact host/path pairs are now accepted; wildcard hosts, foreign identities, mismatched host/path formats, credentials, fragments, non-HTTPS URLs, redirects and nondefault ports remain refused. Provider URLs still come only from authenticated metadata, never email text.

## Implemented behavior

- Optional server-only `RESEND_RECEIVING_API_KEY` takes precedence for metadata and receiving SDK clients. Existing full-access installations can continue through `RESEND_API_KEY` as a backward-compatible fallback. Sending/authentication retains its original credential and code path. Incomplete receiving setup fails by variable name, without echoing values. No native contract, source ID, admission policy, Outbox, formula, migration, agent or polling loop is added.
- The reader's optional diagnostic callback receives only a closed reason and valid integer HTTP error status. Known restricted/invalid/access/quota/rate-limit/not-found responses can be distinguished in server logs without raw SDK error messages, headers, email/file identities, keys or signed URLs. Unknown/invalid values become `PROVIDER_ERROR` / null. A failed diagnostic callback cannot change the existing private `EMAIL_ATTACHMENT_PROVIDER_UNAVAILABLE` retry contract.
- Existing exact identity, declared type/size, expiry, budget reservation, authority recheck, bounded streaming and SHA-256 proof remain in force. Neither metadata nor a retry creates a canonical source or bypasses explicit admission.

Full access includes management of account resources; do not broaden/replace the existing sending key. No new provider spend, domain/DNS change or outbound message is authorized by this code.
2. Provision the approved dedicated key as production Vercel Secret `RESEND_RECEIVING_API_KEY` through the secure credential handoff; never print or commit it, pass it in command arguments, put it in a file, export the old Secret or expose it to the native client. Preserve the existing webhook/signing secret and sender/recipient binding.

A request/retry is not proof of retention.
5. Verify the existing real receipt/file reaches ready with immutable checksum/size proof and one private original, then obtain explicit in-chat admission. 6. On rollback preserve receipt/job/original identities and pending work. Retain the prior API deployment; disable the receiving webhook before rolling back to an incompatible receiver.

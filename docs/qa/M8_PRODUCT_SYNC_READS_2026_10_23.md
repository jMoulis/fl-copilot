# Product catalogue reads during synchronization — 23 October 2026

## Reproduced issue

The production product list and editor/detail hooks included the aggregate pending count in their focus-effect dependencies. A new test using the real hooks, migrated SQLite, serialized writes and 500 products / 500 codes / 1,000 aliases / 7,000 product-day projections reproduces **1,200 SQL statements and 600,000 rows** for the list on 300 synchronization-counter changes. The editor similarly executes **1,200 statements / 1,200 rows**. Both regression cases fail on the previous implementation. This is unnecessary work from progress notifications, not 300 product edits or a demonstrated network/provider error.

## Change

The two readers reuse one stable revision while synchronization is active, then refresh when it settles or a successful pull changes its timestamp, including unchanged aggregate counters. Entry and return always read local SQLite even during a blocked network exchange; an existing snapshot is never used as a reason to skip a fresh navigation read. The explicit list refresh remains available. Slow initial reads can finish without being discarded/restarted for every counter render; stale reads from an old focus remain ignored.

Outside active synchronization, catalogue invalidation uses the pending **command** count rather than all local work. SyncProvider already reads that Outbox count; exposing it as optional local context metadata adds no SQL, timer, queue, public API or migration. The visible aggregate pending count and its detailed jobs remain unchanged. Legacy contexts without this metadata retain their previous aggregate-count fallback. A real change in the command count, conflict/failure count or successful pull still invalidates the reader.

An explicit editor save during synchronization starts a fresh local read without waiting for it to acknowledge the already committed write. A refused stale save refreshes the actual snapshot/conflict even if it created no command and the network has not settled. The canonical transactional writer, expected snapshot, stable IDs, Outbox, source observations, units and retry behavior are unchanged. A read failure retains displayed local content and its existing error; it never deletes data or turns missing values into zero.

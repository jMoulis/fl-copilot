# Today visuals and persistent Actions context

## Behavior and scope

Today priorities and key movements reuse the existing approved product visual library. One focused shared library supplies the entire overview; rows do not create their own library subscription. Existing asset approval, ownership, revocation, cache and bounded preview transfer rules still apply. Rendering uses cached pixels or the existing neutral placeholder and does not wait for a network response. An empty overview does not mount a visual reader. No image generation, provider change or new native dependency is introduced.

Priority cards separate a short action heading, product name, factual amount/comparison and rank. The full title, rank, fact and reason remain in the accessibility label; existing priority-detail and product navigation remain unchanged. A declining waste amount uses a downward numerical arrow with a favourable colour, instead of the previous misleading green upward arrow. Monetary values, source observations, thresholds and ranking are unchanged; at most three main priorities remain the rule.

Actions persists its ISO Monday and checklist filter in the existing local metadata table, privately scoped to the active store and owner. These are presentation preferences, not business commands or synchronized execution declarations. The store date uses Europe/Paris across midnight. Changing a filter never records a task as done. Other execution-view callers keep their existing internal filter behavior. The execution editor remains keyed by week rather than plan revision, preserving its draft through an ordinary plan refresh; existing stale-plan guards still apply when saving.

An initial Actions visit reads the local plan even while synchronization runs. Already displayed same-week content remains in place during intermediate counter changes, then refreshes on settle or on a successful pull whose counters did not change. Hidden screens do not repeatedly read plans. A failed read retains displayed actions and offers a local retry. Corrupt or unreadable preference metadata falls back visibly to the current week; a failed preference write keeps the immediate selection and explains that restart persistence failed. Changing owner/store remounts the scoped view and ignores late former-scope results. This increment does not persist scroll after process termination or change business conflict policies.

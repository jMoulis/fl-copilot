# Store email reception under Actions — 3 November 2026

## Owner arbitration and acceptance target

The owner accepted real reception/original opening, then explicitly requested one stable address per store, all reception under Actions and removal of reception from the Copilot. This supersedes the conversation-bound entry in M7-T23. Existing sender restrictions, private owner/store permissions, original retention, explicit admission, canonical processing and synchronization remain. This is not automatic publication or permission to run an AI turn on email arrival.

The new destination is **Actions → Recevoir des documents par email**. Configuration/copy, received-file list, original recovery, admission and existing processing controls reuse EmailInbox and the current repositories/endpoints. The Copilot no longer mounts an inbox, indicator, email modal or email attachment-menu action. The email-only chat capacity override and address-retirement controls are removed from this UI.

## Reuse and compatibility

No new collection, SQL table, agent, runner, prompt, endpoint or provider is introduced. The legacy `conversationId` transport/cache field remains to preserve immutable manifests, signed byte proofs, existing queued commands and older clients. For the store mailbox its value is the store ID, an explicit storage namespace, **not a fake conversation**. Neither a conversation nor a chat message is created for that namespace. Existing conversation-scoped receipts keep their original identity; active owned historical receipts remain available from the store inbox.

A unique partial index on the existing binding collection enforces one store mailbox, retaining an opaque binding ID. Mongo migration 55 adds only this index and rewrites no existing record. Concurrent setup and retries return the same recipient rather than minting extra addresses. Sender and owner cannot be silently retargeted. Once the store mailbox exists, new legacy chat bindings are refused and old aliases stop accepting new inbound envelopes. Their existing records, retained originals and jobs are not revoked/deleted or rewritten. Deleted-chat legacy records are not resurrected.

Existing manager/owner/store authorization remains; this increment does not broaden private receipt access across accounts. The mailbox is unique for a store; another account cannot create a second mailbox or silently take ownership of the existing one. Owner-transfer or multi-manager delegation is not introduced by changing the UI destination.

Source processing, including resumed historical admissions, never appends a new chat message. Store source processing uses the existing canonical PDF/photo services without a chat attachment. Mercalys uses the existing deterministic importer and transactional operation ledger, with its acknowledged email admission as the trusted transaction guard instead of requiring a chat message. The guard is a runtime callback, never a model/JSON authority argument; it runs for replay and before/after writes. Batch/source proof, scope, cancellation, publication and Outbox behavior remain required. No status messages are emitted in the chat for store imports; batch items and existing processing controls own their progress.

1. Open Actions → Recevoir des documents par email. Configure once, copy the address, leave/reopen: the address is unchanged and the list remains readable offline after loading.
2. Send a real PDF to that address. Refresh, open its retained original, and explicitly choose processing if desired. The resulting document appears in the existing document list without creating a Copilot conversation/message.
3. Reopen/synchronize and retry an already processed file: no duplicate source/publication. For XLSX/ZIP, use the existing import detail to resolve real ambiguities; do not restore a chat import UI.
